# CodeMate 사업계획서 초안

> **한 문장 소개**  
> CodeMate는 주니어 개발자가 AI 답변을 실무 맥락에서 검증하고, 시니어 개발자와의 커뮤니티·멘토링 연결을 통해 스스로 문제를 해결하는 역량을 쌓도록 돕는 개발자 성장 플랫폼이다.

## 작성 기준

이 문서는 완성된 사업계획서가 아닌 전체 초안이다. 조사로 확인한 사실, 현재 구현 상태, 향후 실행 계획을 구분해 서비스의 문제부터 실행까지 하나의 흐름으로 정리한다.

| 구분 | 이 문서에서 다루는 내용 |
| --- | --- |
| 확인한 사실 | 주니어 개발자 27명 대상 자체 설문 결과 |
| 현재 상태 | 기획 방향 확정 및 구현된 MVP 기능 |
| 향후 계획 | 사용자 검증, 기능 개발, 초기 사용자 확보 계획 |

## 1. 문제인식

### 1.1 해결하려는 문제

초기·주니어 개발자는 오류를 반복적으로 경험하고 AI를 적극 활용한다. 그러나 AI 답변이 자신의 코드 구조·환경·이전 시도와 맞는지 판단하기 어렵고, 실무 경험을 가진 시니어에게 도움을 요청할 통로도 부족하다. 빠른 답변은 받지만, 답변을 검증하고 다음 문제에 재사용할 수 있는 해결 경험은 충분히 쌓이지 않는 문제가 있다.

### 1.2 확인한 사실: 자체 설문 결과

설문은 주니어 개발자 중심의 27명을 대상으로 진행했다. 응답자의 70.3%(19명)는 개발 경험 3년 이하 또는 개발 경험이 없었다. 복수응답 문항의 개발 분야는 웹 프론트엔드 51.9%(14명), 모바일 40.7%(11명), 게임 개발 29.6%(8명), 웹 백엔드 22.2%(6명) 순으로 나타났다.

| 설문 결과 | 수치 | 문제 해석 |
| --- | ---: | --- |
| 오류를 보통 이상 경험 | 96.3% (26명) | 오류 해결은 일부 사용자의 예외 상황이 아니라 반복되는 개발 경험이다. |
| 오류 해결에 AI 활용 | 88.9% (24명) | AI는 이미 주된 문제 해결 도구로 자리 잡았다. |
| AI 답변 정확성에 불만 | 51.9% (14명) | 답변을 신뢰·검증하기 어렵다는 문제가 남아 있다. |
| 시니어 도움이 필요했던 경험 | 55.6% (15명) | 실무 판단과 경험 전수에 대한 수요가 존재한다. |
| 오류 해결 시 주변 사람·선배에게 질문 | 18.5% (5명) | 도움 필요 경험과 실제 요청 사이에 접근성·시간·심리적 비용의 장벽이 있을 가능성이 있다. |
| 공식 문서 확인 | 0.0% (0명) | 응답자 집단에서 공식 근거를 확인하는 습관이 낮게 나타났다. |

AI 활용률 88.9%와 AI 정확성 불만 51.9%는 “AI를 더 많이 제공하는 것”만으로 문제를 해결하기 어렵다는 점을 보여 준다. 또한 시니어 도움이 필요했던 비율 55.6%와 직접 질문 비율 18.5%의 차이 37.1%p는 서로 다른 문항을 비교한 참고 지표이며, 도움 요청 장벽을 검증해야 할 가설로 사용한다.

### 1.3 문제의 원인

1. **맥락 부족**: 오류 로그만으로는 프로젝트 구조, 사용 기술, 이전 시도, 제약 조건을 반영하기 어렵다.
2. **검증 부족**: AI 답변이 왜 맞는지, 내 코드에 적용해도 되는지 판단하기 어렵다.
3. **경험 전수 부족**: 시니어 판단이 필요한 순간에도 질문할 대상과 관계가 없어 도움 요청이 실제 행동으로 이어지지 않는다.

## 2. 해결방법 및 실현가능성

### 2.1 해결 방식

CodeMate는 문제 입력부터 해결 기록, 사람 간 연결까지의 흐름을 제공한다.

1. 사용자가 오류 로그, 사용 기술, 코드 맥락, 이전 시도를 구조화해 기록한다.
2. 사용자는 해결 과정과 검증 결과를 저장해 이후 유사 문제에 재사용한다.
3. 프로필과 커뮤니티에서 기술 스택, 관심 분야, 프로젝트 경험을 공유한다.
4. 고난도 판단이나 성장 상담이 필요한 경우 시니어와 커피챗·멘토링·프로젝트 모집으로 연결한다.
5. 활동 후 후기와 기록을 남겨 신뢰 가능한 관계와 학습 이력을 축적한다.

### 2.2 차별성

일반 생성형 AI는 빠른 답변을 제공하지만, 사용자별 맥락 검증과 지속적인 성장 기록에는 한계가 있다. 일반 개발 커뮤니티는 질문과 답변을 제공하지만, 개인의 해결 기록과 시니어·주니어 간 관계 형성을 하나의 흐름으로 연결하지 않는다.

CodeMate는 AI를 즉시 정답을 만드는 기능으로만 보지 않는다. 오류 맥락을 기록하고, 해결 과정을 재사용하며, 시니어의 실무 판단과 장기적인 관계로 이어지는 구조를 만든다.

### 2.3 현재 상태: 구현된 MVP 기반

현재 Spring Boot 기반 MVP에 다음 기능을 구현했다.

- 주니어·시니어 역할 구분 회원가입과 JWT 기반 로그인
- 시니어 가입 승인 대기 및 관리자 승인·반려
- 오류 기록 등록, 조회·검색, 상태 변경, 관리자 삭제
- 사용자 프로필 입력과 제한된 CSS 기반 프로필 카드 꾸미기
- MySQL 및 화면 미리보기용 H2 데이터베이스 구성

현재 구현은 오류 기록과 회원·권한·프로필의 기본 흐름까지다. AI 분석, 공개 범위, 프로젝트 포트폴리오, 게시판, 팔로우, 커피챗, 멘토링 매칭은 아직 구현 전이므로 향후 계획으로 구분한다.

### 2.4 실현 가능성

- 현재 MVP는 Java 17, Spring Boot, Thymeleaf, Spring Data JPA, MySQL 기반으로 구현돼 있다.
- 회원·권한·관리자 승인·오류 기록 기능이 있어 이후 게시판과 관계 기능의 사용자·권한 기반으로 활용할 수 있다.
- AI 기능은 MVP 핵심 기능으로 즉시 도입하지 않고, 사용자 검증 후 오류 맥락 정리·근거 제시·대화 요약 등 보조 기능부터 검토한다.
- 초기에는 금전 결제, 현상금, 정산을 제외해 운영·법적 복잡도를 낮춘다.

## 3. MVP 현황

### 3.1 현재 구현 기능

| 영역 | 구현 상태 | 설명 |
| --- | --- | --- |
| 회원·인증 | 구현 | 주니어·시니어 역할 구분, 로그인, JWT 쿠키 인증 |
| 시니어 검증 | 구현 | 시니어 가입 대기, 관리자 승인·반려 |
| 오류 기록 | 구현 | 오류 등록, 목록·검색, 상세 조회, 상태 변경 |
| 관리자 | 구현 | 시니어 승인 관리, 오류 기록 삭제 권한 |
| 프로필 | 기본 구현 | 표시 이름, 소개·경력, 기술 스택, 관심 분야, 포트폴리오 링크 |
| AI 분석 | 미구현 | 현재는 AI 연결 없이 향후 검증 대상 |
| 게시판·댓글 | 미구현 | 3단계 개발 대상 |
| 팔로우·모집·커피챗 | 미구현 | 4단계 개발 대상 |

### 3.2 MVP 검증 목표

초기 MVP는 완성도보다 문제 가설 검증을 우선한다.

- 오류 기록 기능을 실제 사용자가 반복적으로 사용하는지 확인한다.
- 사용자가 어떤 오류 맥락을 남기는지 확인한다.
- 해결 기록을 재사용하는지 확인한다.
- 시니어 검토·커피챗·멘토링 연결에 대한 요청이 실제로 발생하는지 확인한다.

## 4. 시장 및 경쟁

### 4.1 목표 사용자

초기 목표 사용자는 개발 경험이 없거나 3년 이하인 예비·주니어 개발자다. 설문 응답자의 70.3%가 이 범주에 포함돼 있어, 오류 해결과 실무 판단의 어려움을 먼저 검증할 수 있는 집단으로 본다.

이후 시니어 개발자, 개발 동아리, 스터디·프로젝트 운영자까지 확장한다. 시니어는 전문성 공개, 멘토링·피드백 활동 기록, 커뮤니티 내 네트워크 형성을 얻는다.

### 4.2 경쟁 환경과 차별화 방향

| 대안 | 사용자가 얻는 가치 | 한계 | CodeMate의 대응 |
| --- | --- | --- | --- |
| 생성형 AI | 빠른 답변과 코드 예시 | 맥락 부정확성, 신뢰도 판단의 어려움 | 오류 맥락·검증 과정·해결 기록을 구조화 |
| 검색·공식 문서 | 신뢰 가능한 기술 정보 | 초보자가 필요한 정보를 찾고 적용하기 어려움 | 해결 과정에서 근거 확인 습관을 돕는 흐름 설계 |
| 일반 개발 커뮤니티 | 다양한 질문·답변 | 개인의 성장 기록과 지속 관계가 분리됨 | 프로필, 활동 기록, 커피챗·멘토링을 연결 |
| 멘토링 서비스 | 경험 많은 사람의 조언 | 일회성 연결 또는 높은 접근 비용 | 시니어 승인, 공개 프로필, 커뮤니티 활동을 바탕으로 관계 형성 |

### 4.3 검증이 필요한 경쟁 가설

설문은 AI 답변의 신뢰 문제와 시니어 도움 수요를 보여 주지만, 사용자가 실제로 프로필 작성·게시판 활동·멘토링 요청까지 이어질지는 아직 확인하지 못했다. 초기 사용자 테스트로 기능별 사용 전환과 재방문을 검증한다.

## 5. 사업화 및 실행 계획

### 5.1 단계별 개발 계획

| 단계 | 개발 내용 | 검증 질문 |
| --- | --- | --- |
| 1단계 | 인증, 역할 권한, 시니어 승인 안정화 | 역할별 서비스 이용 흐름이 정상적으로 작동하는가 |
| 2단계 | 프로필 고도화, 공개 범위, 프로젝트·포트폴리오 | 사용자가 자신의 경험과 관심 분야를 충분히 표현하는가 |
| 3단계 | 개발·자유·건의 카테고리 게시판, 댓글, 검색, 신고 | 사용자가 기술 질문과 정보를 지속적으로 교류하는가 |
| 4단계 | 개인·동아리 팔로우, 모집글, 커피챗, 후기, 상호 평가 | 관계 기능이 실제 만남과 반복 활동으로 이어지는가 |
| 5단계 | 멘토링 요청·수락·진행 기록, 사용자 테스트 | 시니어·주니어 관계가 2주 이상 유지되는가 |

### 5.2 초기 사용자 확보 계획

- 교내 개발 동아리, 전공 수업, 스터디를 중심으로 초기 사용자를 모집한다.
- 설문 응답자와 유사한 초기·주니어 개발자를 대상으로 사용성 테스트를 진행한다.
- 시니어는 졸업생, 현직 개발자 멘토, 동아리 선배를 대상으로 검증된 참여자를 확보한다.
- 테스트 후 인터뷰를 통해 오류 기록, 게시판, 커피챗·멘토링 중 실제 효용이 큰 기능을 우선 개선한다.

### 5.3 핵심 성과 지표

| 지표 | 측정 방법 | 초기 목표 |
| --- | --- | ---: |
| 프로필 완성률 | 가입 후 프로필을 완성한 사용자 비율 | 60% 이상 |
| 첫 활동 완료율 | 가입 후 첫 오류 기록·게시글·댓글 작성 비율 | 50% 이상 |
| 해결 기록 재사용률 | 저장한 해결 기록을 다시 조회·활용한 비율 | 측정 후 목표 설정 |
| 커피챗·멘토링 요청 수락률 | 전체 요청 중 수락 비율 | 40% 이상 |
| 첫 소통 완료율 | 매칭 후 첫 질문 또는 피드백이 작성된 비율 | 70% 이상 |
| 2주 이상 관계 유지율 | 2주 이상 활동한 관계 비율 | 50% 이상 |

목표 수치는 초기 검증을 위한 가설이며, 실제 사용자 테스트 결과에 따라 조정한다.

## 6. 팀 구성 및 실행력

### 6.1 현재 확인된 팀 구성

설문 자료 표지 기준 팀원은 이수용, 정준호, 송지은, 최예은, 한별 총 5명이다. 현재 구현된 Spring Boot MVP와 설문 설계·분석 자료는 팀이 문제 조사와 초기 제품 개발을 함께 진행하고 있음을 보여 준다.

### 6.2 역할 분담 초안

역할은 팀 내부 합의 후 확정해야 하며, 아래는 사업계획서에 채울 수 있는 분담 초안이다.

| 역할 | 주요 책임 |
| --- | --- |
| 기획·PM | 사용자 조사, 문제 정의, 기능 우선순위, 일정 관리 |
| 백엔드 | 인증·권한, 데이터 모델, API, 관리자 기능 |
| 프론트엔드·UX | 사용자 흐름, 반응형 화면, 사용성 테스트 반영 |
| 데이터·AI 검토 | 설문 분석, AI 보조 기능의 검증 범위 설계 |
| 커뮤니티 운영·검증 | 시니어 섭외, 초기 사용자 모집, 인터뷰·피드백 관리 |

### 6.3 실행력 보완 계획

- 기능 개발 전후로 사용자 인터뷰와 사용성 테스트를 반복한다.
- 시니어 승인, 신고, 비공개 평가 등 신뢰·안전 기능은 관리자 권한으로 단계적으로 도입한다.
- 결제·정산·현상금은 초기 범위에서 제외하고, 관계 형성과 재방문 지표가 확인된 후 사업 모델을 검토한다.
