# DebugMate 프로젝트 핵심 방향성 변경 보고서

- 작성일: 2026년 10월 29일
- 프로젝트명: DebugMate
- 작성 목적: 사업 모델 검토 과정과 교수 피드백 이후 확정된 방향을 기록하고, 향후 MVP 개발 기준을 명확히 정의한다.

## 1. 보고서 요약

DebugMate는 처음에 AI가 주니어 개발자의 오류를 분석하고, 해결하기 어려운 문제를 시니어 개발자에게 연결하는 서비스로 기획되었다. 이후 시니어 참여에 대한 보상과 초기 사용자 수 부족 문제를 해결하기 위해 현상금 기반 오류 해결 커뮤니티를 검토했다.

그러나 교수 피드백을 반영하여 프로젝트의 핵심 가치를 다시 검토한 결과, 단발성 오류 해결 경쟁보다 시니어와 주니어 간의 지속적인 관계 형성과 경험 전수가 본 프로젝트에 더 적합하다고 판단했다. 이에 따라 최종 방향을 장기적인 튜터 매칭 및 멘토링 관계 지원 플랫폼으로 확정한다.

최종 서비스 방향은 다음과 같다.

> DebugMate는 시니어 개발자와 주니어 개발자의 만남을 주선하고, 프로젝트 중심의 지속적인 소통과 실무 경험 전수를 지원하는 멘토링 플랫폼이다.

## 2. 최초 기획 방향

### 2.1 서비스 구조

최초 기획은 다음과 같은 오류 해결 흐름을 중심으로 구성되었다.

1. 주니어 개발자가 코드와 오류 로그를 입력한다.
2. AI가 오류 원인과 수정 방법을 분석한다.
3. 사용자가 AI 답변을 적용하고 결과를 검증한다.
4. AI로 해결하지 못한 문제는 시니어 개발자에게 검토를 요청한다.
5. 해결 결과를 저장하여 다시 활용한다.

### 2.2 최초 기획의 목적

- 개발 오류 해결에 필요한 시간을 줄인다.
- AI 답변의 원인과 검증 절차를 함께 제공한다.
- 해결 기록을 개인의 학습 자료로 축적한다.
- AI로 해결하기 어려운 문제를 시니어 개발자의 경험으로 보완한다.

## 3. 최초 기획에서 발견된 문제

### 3.1 시니어 참여 동기 부족

최초 구조에서 주니어는 문제 해결이라는 명확한 이익을 얻지만, 시니어는 자신의 시간과 전문성을 제공해야 했다. 시니어에게 돌아가는 보상이나 장기적인 관계 형성의 가치가 명확하지 않아 충분한 공급자를 확보하기 어렵다는 문제가 제기되었다.

### 3.2 AI 의존의 반복

AI를 사용해 작성한 코드를 충분히 이해하지 못한 상태에서 오류가 발생하고, 해당 오류를 다시 AI에 의존해 해결하면 주니어의 실질적인 역량이 향상되지 않을 가능성이 있다. 단순한 수정 코드 제공은 당장의 문제를 해결할 수 있지만 문제 접근 방식과 설계 판단 능력을 길러주지는 못한다.

### 3.3 단발성 관계

오류 한 건을 해결하면 주니어와 시니어의 연결이 종료되는 구조였다. 이러한 방식으로는 시니어가 가진 설계 철학, 협업 방식, 기술 선택 기준과 같은 경험 기반 지식을 충분히 전달하기 어렵다.

### 3.4 기존 AI 서비스와의 차별성 부족

오류 분석과 수정 코드 제공만으로는 기존 생성형 AI 서비스와 뚜렷하게 구분되기 어렵다. AI API를 연결하는 것만으로 독립적인 플랫폼 가치를 증명하기에는 한계가 있었다.

## 4. 현상금 기반 커뮤니티 검토

### 4.1 현상금 모델을 검토한 이유

시니어 참여 동기를 구체화하고 초기 1대1 매칭에 필요한 사용자 규모 문제를 완화하기 위해 현상금 기반 오류 해결 커뮤니티를 대안으로 검토했다.

검토한 흐름은 다음과 같다.

1. 주니어가 오류 게시글과 현상금을 등록한다.
2. 여러 개발자가 해결안을 제출한다.
3. 질문자가 해결안을 직접 테스트한다.
4. 정상 작동한 답변을 채택한다.
5. 채택된 답변자가 현상금을 받는다.

### 4.2 기대했던 장점

- 시니어 또는 숙련 개발자에게 직접적인 참여 동기를 제공할 수 있다.
- 실시간 1대1 매칭 없이 비동기 방식으로 운영할 수 있다.
- 여러 답변자가 해결안을 제시해 답변 품질을 비교할 수 있다.
- 해결된 질문과 답변을 검색 가능한 개발 지식으로 축적할 수 있다.

### 4.3 현상금 모델의 한계

- 문제를 가장 빨리 해결하는 경쟁에 집중될 수 있다.
- 시니어와 주니어의 관계가 답변 채택 이후 종료될 가능성이 높다.
- 문제 해결 결과는 얻을 수 있지만 주니어의 장기적인 성장까지 보장하기 어렵다.
- 답변 복제, 미채택, 오답, 현상금 분쟁을 관리하는 기능이 필요하다.
- 실제 현금을 사용할 경우 결제, 환불, 정산과 운영 정책이 추가되어 MVP 범위가 커진다.
- 경험 전수라는 프로젝트의 가치보다 거래와 경쟁이 서비스의 중심으로 인식될 수 있다.

## 5. 교수 피드백 이후 재검토

교수 피드백을 반영하여 프로젝트가 해결하려는 본질적인 문제가 무엇인지 다시 검토했다. 핵심 질문은 단순히 오류를 빠르게 해결하는 것인지, 또는 주니어 개발자가 시니어의 경험을 통해 실질적으로 성장하도록 돕는 것인지였다.

논의 결과, 본 프로젝트가 제공해야 하는 핵심 가치는 개별 오류의 외주형 해결보다 다음 항목에 있다고 판단했다.

- 시니어와 주니어가 서로 만날 수 있는 접점을 제공한다.
- 단발성 답변을 넘어 지속적인 멘토·멘티 관계를 만든다.
- 실제 프로젝트를 중심으로 실무 경험과 판단 기준을 전수한다.
- 주니어가 스스로 문제를 해결할 수 있는 역량을 기르도록 돕는다.
- AI는 사람을 대체하지 않고 멘토링을 정리하고 보조한다.

따라서 현상금 모델은 참여 보상 문제에 대한 하나의 해결책이지만, 프로젝트가 지향하는 인간적인 교류와 기술 전승을 충분히 구현하지 못한다고 결론 내렸다.

## 6. 최종 확정 방향

### 6.1 서비스 정의

DebugMate의 최종 방향을 AI 오류 해결 서비스나 현상금 경쟁 커뮤니티가 아닌, 시니어와 주니어 개발자의 지속적인 만남을 지원하는 튜터 매칭 플랫폼으로 확정한다.

### 6.2 핵심 이용 흐름

1. 시니어 개발자가 전문 분야, 경력, 지도 가능한 기술과 멘토링 방식을 등록한다.
2. 관리자가 시니어의 경력과 포트폴리오를 확인하고 가입을 승인한다.
3. 주니어 개발자가 관심 기술과 현재 진행 중인 프로젝트를 등록한다.
4. 주니어가 적합한 시니어를 검색하고 멘토링을 신청한다.
5. 시니어가 신청 내용을 확인하고 수락하거나 거절한다.
6. 매칭이 성사되면 전용 소통 공간에서 프로젝트와 학습 과정을 공유한다.
7. 양측이 목표, 피드백과 진행 기록을 지속적으로 관리한다.
8. 멘토링 종료 후 상호 평가와 활동 기록을 남긴다.

### 6.3 시니어 참여 원칙

초기 MVP는 금전적 보상을 전제로 하지 않는다. 자신의 경험과 지식을 후배에게 전수하려는 시니어의 자발적인 참여를 기반으로 서비스 수요와 관계 지속 가능성을 먼저 검증한다.

시니어에게 제공할 비금전적 가치는 다음과 같다.

- 전문 분야와 경력을 보여주는 공개 프로필
- 멘토링 활동 및 기여 기록
- 주니어의 성장에 기여했다는 사회적 보람
- 개발 커뮤니티 내 평판 형성
- 후배 개발자와의 네트워크 확대

장기적으로는 사용자 조사 결과에 따라 유료 멘토링, 기업 후원, 인증서 또는 전문가 활동 증명 기능을 검토할 수 있다.

## 7. AI 역할 재정의

AI는 문제 해결의 주체가 아니라 멘토링 과정을 보조하는 기능으로 제한한다.

향후 AI 적용 후보는 다음과 같다.

- 멘토링 대화 요약
- 주차별 학습 내용과 진행 기록 정리
- 시니어 피드백의 핵심 항목 분류
- 다음 학습 목표 초안 작성
- 멘토와 멘티의 관심 기술을 바탕으로 한 매칭 보조
- 반복적으로 발생하는 질문과 학습 어려움 분석

AI가 수정 코드를 즉시 제공하는 기능은 핵심 MVP에서 제외한다. 이를 통해 주니어가 직접 생각하고 시니어와 논의하는 과정을 보호한다.

## 8. 수정된 MVP 범위

### 8.1 MVP 필수 기능

#### 회원 및 권한

- 주니어·시니어 역할 구분 회원가입
- JWT 기반 로그인
- 시니어 가입 승인 대기
- 관리자 승인 및 반려
- 역할별 접근 권한

#### 프로필

- 시니어 경력과 전문 기술 등록
- 포트폴리오 등록
- 지도 가능한 분야 및 시간 등록
- 주니어 관심 기술과 프로젝트 정보 등록

#### 튜터 탐색 및 신청

- 전문 분야별 시니어 목록
- 시니어 프로필 상세 조회
- 멘토링 신청서 작성
- 신청 수락 및 거절
- 매칭 상태 관리

#### 멘토링 공간

- 매칭된 사용자 전용 공간
- 학습 목표 등록
- 질문 및 피드백 작성
- 주차별 진행 기록
- 멘토링 종료 처리

#### 관리자

- 시니어 가입 승인 및 반려
- 회원과 게시글 관리
- 부적절한 콘텐츠 삭제
- 신고 내용 확인

### 8.2 MVP 제외 기능

- 현상금 등록 및 지급
- 실제 결제와 정산
- 답변 경쟁 및 채택
- AI 자동 오류 수정
- 실시간 화상 통화
- 복잡한 추천 알고리즘
- GitHub 자동 연동

## 9. 기존 구현물 처리 방안

현재 구현된 로그인, 역할 구분, 시니어 승인, 관리자 권한과 공통 UI는 변경된 방향에서도 그대로 활용한다.

기존 오류 게시글 기능은 다음과 같이 전환할 수 있다.

| 기존 기능 | 변경 후 활용 방식 |
| --- | --- |
| 오류 등록 | 멘토링 질문 또는 프로젝트 이슈 등록 |
| 해결 기록 | 멘토링 진행 기록 |
| 해결 상태 | 질문 대기·피드백 완료·종료 상태 |
| 시니어 검토 | 매칭된 멘토의 피드백 |
| 관리자 삭제 | 멘토링 게시글 관리 |

현상금과 해결안 경쟁을 전제로 한 기능은 개발 우선순위에서 제거한다.

## 10. 수정된 개발 우선순위

### 1단계: 기존 인증 기능 안정화

- 주니어·시니어·관리자 권한 검증
- 시니어 승인 흐름 완성
- 사용자별 데이터 접근 제한

### 2단계: 사용자 프로필

- 시니어 전문 분야와 경력
- 주니어 관심 분야와 프로젝트
- 포트폴리오 및 활동 가능 시간

### 3단계: 멘토링 신청과 매칭

- 시니어 검색
- 신청서 작성
- 수락·거절
- 매칭 상태 관리

### 4단계: 멘토링 전용 공간

- 목표 설정
- 질문과 피드백
- 진행 기록
- 종료 처리

### 5단계: 관리자 및 사용자 테스트

- 회원 및 콘텐츠 관리
- 신고 처리
- 실제 시니어·주니어 대상 사용성 평가
- 관계 지속 의향과 만족도 조사

## 11. 변경된 성과 지표

현상금 모델의 답변 수나 채택률 대신, 관계 형성과 멘토링 지속성을 측정한다.

| 평가 항목 | 측정 방법 | 초기 목표 |
| --- | --- | ---: |
| 멘토링 신청 수락률 | 전체 신청 중 시니어가 수락한 비율 | 40% 이상 |
| 첫 소통 완료율 | 매칭 후 첫 질문 또는 피드백이 작성된 비율 | 70% 이상 |
| 2주 이상 관계 유지율 | 매칭 후 2주 이상 활동한 팀의 비율 | 50% 이상 |
| 목표 달성률 | 등록 목표 중 완료한 목표의 비율 | 50% 이상 |
| 멘토 재참여 의향 | 시니어 대상 설문 | 60% 이상 |
| 멘티 만족도 | 5점 척도 설문 | 평균 4점 이상 |

초기 목표는 MVP 검증을 위한 잠정 기준이며 실제 사용자 테스트 후 조정한다.

## 12. 최종 결론

DebugMate는 기획 과정에서 세 가지 방향을 검토했다.

1. AI 기반 오류 해결과 시니어 검토
2. 현상금 기반 오류 해결 커뮤니티
3. 시니어·주니어 간 지속형 튜터 매칭

현상금 모델은 시니어 참여 동기와 초기 매칭 문제를 해결할 가능성이 있었지만, 단발성 문제 해결과 경쟁을 중심으로 한다는 한계가 있었다. 교수 피드백 이후 프로젝트의 본질을 다시 검토한 결과, 사람 간의 관계와 경험 전수에 집중하는 것이 기존 AI 서비스와 차별화되고 주니어의 실질적인 성장에도 더 적합하다고 판단했다.

따라서 DebugMate는 다음 방향으로 최종 전환한다.

> 오류를 대신 해결해 주는 서비스가 아니라, 시니어와 주니어 개발자가 만나 실제 프로젝트를 함께 논의하고 장기적으로 성장할 수 있도록 지원하는 튜터 매칭 플랫폼을 구축한다.

향후 MVP 개발은 AI 오류 분석이나 현상금 기능보다 프로필, 멘토 탐색, 멘토링 신청, 매칭 관리와 지속적인 소통 공간을 우선하여 진행한다.
